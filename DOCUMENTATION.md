# AI Integration Slice — Documentation

## 1. What This Is
This slice lets a signed-in user upload a photo or PDF of a receipt and get back structured data — merchant, total, date, and a line-by-line breakdown of items — extracted by a real AI model rather than typed in by hand. The upload happens instantly and processing runs in the background, so the user watches the receipt move from queued to processing to a finished result without the page ever hanging on a slow external call. Once the result is ready, the user can trigger one follow-up action — a plain-language summary of the receipt, generated by a second, lighter model working from the already-extracted data rather than the original image.

Deliberately not included: no editing of the extracted data, no way to browse or search past receipts, no sharing or exporting, and no account system beyond signing in — authentication is reused as-is from Assessment 1 rather than rebuilt. These are left out because the brief asks for one flow, built properly, not a full receipts-management product; anything beyond the single upload-to-result-to-summary path would be scope the assessment explicitly warns against adding.

## 2. How To Run It

**Prerequisites**

- Node.js ≥ 20 (the project uses Next.js 16.3 which requires Node 20+)
- npm (ships with Node)
- A PostgreSQL database (Neon, Supabase, or a local instance)
- A Cloudflare R2 bucket with an API token that has read/write access
- A Gemini API key from Google AI Studio

**Steps**

1. Clone the repository and install dependencies:

```bash
git clone <repo-url> && cd ai-slice
npm install
```

2. Copy `.env.example` to `.env`:

```bash
copy .env.example .env
```

3. Fill in every value in `.env` **by hand** — never let an agent write real keys. The file has placeholder comments explaining where each value comes from. The required variables are listed below.

4. Run the database migration to create all tables:

```bash
npx prisma migrate dev
```

5. Start **two processes in two separate terminals**. Both must be running simultaneously:

**Terminal 1 — the Next.js dev server:**
```bash
npm run dev
```

**Terminal 2 — the background worker:**
```bash
npm run worker
```

The worker (`scripts/worker.ts`, run via `tsx`) is a standalone polling process that picks up PENDING jobs from the database and processes them through the Gemini API. It is not part of the Next.js server — it runs as its own long-lived process alongside it. Without it, uploaded receipts will sit in PENDING forever because the API route only *queues* the job (returning 202 Accepted), it never calls the model.

**It appears at:** `http://localhost:3000`

The upload flow entry point is: `http://localhost:3000/receipts/upload` — this is the actual start of the slice's flow, not the bare homepage. You must be signed in first (authentication is reused from Assessment 1; sign up at `/signup` or sign in at `/signin`).

**Environment variables**

These are every `process.env.*` reference confirmed in the codebase. `.env.example` exists in the repo with commented placeholders for all of them.

| Name | Where it comes from |
|---|---|
| `DATABASE_URL` | Your PostgreSQL provider's connection string (Neon dashboard → Connection Details → pooled URL) |
| `GEMINI_API_KEY` | Google AI Studio → API keys. Typed by hand, never generated by an agent |
| `EXTRACTION_MODEL` | Optional override for the extraction model ID (defaults to a value in `lib/ai/config.ts` if unset) |
| `FOLLOWUP_MODEL` | Optional override for the followup model ID (defaults to a value in `lib/ai/config.ts` if unset) |
| `STORAGE_ACCOUNT_ID` | Cloudflare dashboard → R2 → Overview → Account ID |
| `STORAGE_ACCESS_KEY_ID` | Cloudflare dashboard → R2 → Manage R2 API Tokens → Access Key ID |
| `STORAGE_SECRET_ACCESS_KEY` | Same token page → Secret Access Key |
| `STORAGE_BUCKET` | The name of your R2 bucket (created in Cloudflare dashboard → R2 → Create bucket) |
| `NODE_ENV` | Set automatically by Next.js (`development` in local dev); used directly in `app/api/auth/signin/route.ts` and `app/api/auth/verify/route.ts` to decide whether the session cookie requires HTTPS |

All other tunables (token limits, timeouts, concurrency caps, rate limit windows) live in `lib/ai/config.ts` with working defaults and are optionally overridable via environment variables — see that file for the full list and its comments explaining each value.

## 3. The Flow, Step By Step

Authentication is reused from Assessment 1 — the user must have signed up, verified their email, and signed in before any of the following works. The session check (`lib/auth/session.ts`) reads the `sessionId` cookie and looks up the session in the database; every API route in this slice calls `getCurrentUser()` and returns 401 if there is no valid session.

### Step 1 — The user uploads a receipt

**User:** Navigates to `/receipts/upload` and selects a file (JPEG, PNG, WEBP, or PDF, up to 8 MB).

**Frontend sends:** The upload page (`app/receipts/upload/page.tsx`) performs client-side type and size validation (mirroring the server's rules, but the server check is the one that actually holds), then sends a `POST` with `FormData` containing the file to `/api/receipts/upload`.

**Server does:** The upload route (`app/api/receipts/upload/route.ts`) checks the session, enforces a rate limit (10 uploads per minute per IP via `lib/rate-limit.ts`), validates the file server-side against the shared Zod schema (`lib/validation/upload.ts`), uploads the raw bytes to Cloudflare R2 via `lib/storage/r2.ts` (only the storage key goes into the database — no file content column exists), creates a `Receipt` row and a `Job` row with type `EXTRACTION` and status `PENDING` in a single Prisma create, and returns `202 Accepted` with the receipt ID. It does not call the model — it only queues the work.

**Frontend then:** Redirects the browser to `/receipts/{id}`.

### Step 2 — The user sees the processing state

**User:** Lands on the receipt status page at `/receipts/{id}`.

**Frontend sends:** The status page (`app/receipts/[id]/page.tsx`) immediately fetches `GET /api/receipts/{id}` and begins polling it every 2 seconds.

**Server does:** The status route (`app/api/receipts/[id]/route.ts`) looks up the receipt scoped to the authenticated user's ID inside the query itself (a receipt that belongs to someone else returns 404, not someone else's data), includes the jobs, extraction result, and latest followup result, and returns the current state: extraction status (PENDING, PROCESSING, DONE, or FAILED), the parsed result if done, and the latest followup if one exists.

**Frontend then:** Displays "Queued — waiting to start…" or "Processing your receipt…" while the job is PENDING or PROCESSING. Continues polling until extraction finishes.

### Step 3 — The worker extracts the receipt

**What happens (no user action):** The worker process (`scripts/worker.ts`) polls the `Job` table every 3 seconds for PENDING rows, ordered oldest-first (FIFO). It claims up to `AI_CONFIG.queue.concurrency` jobs (default 3) at a time by setting their status to PROCESSING.

For an EXTRACTION job, the worker downloads the file from R2 (`lib/storage/r2.ts` → `downloadFromR2`), calls the Gemini model via `lib/ai/gemini.ts` → `extractReceipt()`. This function sends the image/PDF as base64 inline data with the extraction system prompt (`lib/ai/prompts/extraction.ts`), requests structured JSON output constrained by `GEMINI_EXTRACTION_RESPONSE_SCHEMA`, and — regardless of what the provider did — validates the parsed JSON against the Zod `extractionResultSchema` (`lib/ai/schemas/extraction.ts`). If validation fails, it retries up to `maxAttempts` (default 3) with a linear backoff.

On success, the worker upserts an `ExtractionResult` row with both the raw response and the validated/parsed fields (merchant, totalMinor, currency, purchaseDate, lineItems), then marks the job DONE. On failure after all retries, it marks the job FAILED with the error message.

### Step 4 — The user sees the result

**User:** The polling page picks up the DONE status and stops polling. The result view appears showing: merchant name, total (formatted from minor units), purchase date, and each line item with description, quantity, and amount.

**Frontend:** Renders the extraction result directly from the status API response. No separate fetch needed — the polling loop already has the data.

### Step 5 — The user triggers a follow-up action

**User:** Clicks the "Summarize" button below the extraction result.

**Frontend sends:** A `POST` to `/api/receipts/{id}/followup` with `{ "action": "summarize" }` (`app/receipts/[id]/page.tsx`).

**Server does:** The followup route (`app/api/receipts/[id]/followup/route.ts`) checks the session, enforces a separate rate limit (5 followup actions per minute per IP), validates the action is one of `summarize`, `rephrase`, or `expand` via a Zod schema, confirms the receipt belongs to this user and that extraction has actually finished (returns 409 if not — there is nothing to summarize yet), then creates a new `Job` row with type `FOLLOWUP`, the chosen action, and status `PENDING`. Returns `202 Accepted`.

**Frontend then:** Bumps a `pollKey` state variable, which restarts the polling effect — necessary because the original polling loop had already stopped itself when extraction finished DONE, so without restarting it the page would never notice the followup completing.

### Step 6 — The worker runs the follow-up

**What happens (no user action):** The worker picks up the FOLLOWUP job, reads the `action` field from the Job row, loads the `ExtractionResult` for that receipt, and calls `lib/ai/gemini.ts` → `runFollowup()`. This sends the already-validated extraction data as text (no image — the followup role never sees the original file) with the followup system prompt (`lib/ai/prompts/followup.ts`) to a different, lighter model (`gemini-3.1-flash-lite`). The response is plain text, not JSON.

On success, the worker creates a `FollowupResult` row with the action and result text, then marks the job DONE.

### Step 7 — The user sees the follow-up result

**User:** The resumed polling loop picks up the followup DONE status. The summary text appears in a styled box below the extraction result. Polling stops again.

## 4. The Data Model

The authentication tables (`User`, `Session`, `VerificationCode`, `PasswordResetToken`, `RateLimit`) are reused verbatim from Assessment 1 so that foreign keys line up on a fresh migration. They are not documented here — see Assessment 1's documentation.

### `Receipt`

Holds metadata about one uploaded file. The file itself lives in R2 — this table stores only the key to find it.

| Column | Type | Constraint | Decision |
|---|---|---|---|
| `userId` | `String` | FK → User, `onDelete: Cascade` | Scopes every query to the owning user. Cascade means deleting a user cleans up their receipts automatically rather than leaving orphans. Indexed (`@@index([userId])`) because the user's receipt list is always filtered by this column. |
| `storageKey` | `String` | `@unique` | The R2 object key. Unique because two receipts pointing at the same object would be a data integrity bug — each upload produces its own key (`{prefix}/{userId}/{uuid}-{filename}`). |
| `originalFilename` | `String` | not null | The user's original filename, preserved for display. Not used as a storage key (that would collide). |
| `mimeType` | `String` | not null | The validated MIME type (`image/jpeg`, `image/png`, `image/webp`, `application/pdf`). Stored because the worker needs it when sending the file to Gemini — the R2 download does not carry it. |
| `sizeBytes` | `Int` | not null | The validated file size. Stored for display and audit rather than re-fetching from R2. |

### `Job`

The queue. Each row represents one unit of work for the worker to pick up, process, and mark done or failed.

| Column | Type | Constraint | Decision |
|---|---|---|---|
| `receiptId` | `String` | FK → Receipt, `onDelete: Cascade` | Links the job to its receipt. Cascade: if a receipt is deleted, its jobs are no longer meaningful. Indexed (`@@index([receiptId])`) because the status page looks up a receipt's jobs. |
| `type` | `JobType` enum | not null | `EXTRACTION` or `FOLLOWUP`. An enum rather than a free string because only these two types exist and the worker branches on them — a typo in a string would silently do nothing. |
| `action` | `String?` | nullable | The specific followup action (`summarize`, `rephrase`, `expand`). Nullable because EXTRACTION jobs have no action — making it required would force a meaningless placeholder on every extraction job. |
| `status` | `JobStatus` enum | `@default(PENDING)` | `PENDING` → `PROCESSING` → `DONE` or `FAILED`. Defaulting to PENDING means the creation site only needs to set the type, not remember to also set the initial status. Indexed together with `createdAt` (`@@index([status, createdAt])`) because the worker's poll query is `WHERE status = PENDING ORDER BY createdAt`. |
| `attempts` | `Int` | `@default(0)` | Tracks retry count. Defaults to 0 rather than 1 because the count is incremented when a retry happens, not when the job is created. |
| `errorMessage` | `String?` | nullable | The error text from a failed job. Nullable because successful jobs have no error. Stored so the status page can show the user what went wrong, and so evidence screenshots can prove the error was captured. |
| `startedAt` | `DateTime?` | nullable | When the worker began processing. Nullable because a PENDING job has not started yet. |
| `completedAt` | `DateTime?` | nullable | When the job finished (successfully or not). Nullable because an in-progress job has not completed yet. Together with `startedAt`, allows measuring processing duration. |

### `ExtractionResult`

The validated output from the extraction model for one receipt.

| Column | Type | Constraint | Decision |
|---|---|---|---|
| `receiptId` | `String` | `@unique`, FK → Receipt, `onDelete: Cascade` | **Unique** — one receipt gets exactly one extraction result. A re-extraction is an upsert (overwrite), not a second row. This constraint is what makes duplicate extraction results impossible at the database level rather than merely undesired at the application level. |
| `rawResponse` | `Json` | not null | The complete, unmodified JSON the model returned, before any validation or transformation. Stored so the raw output can be compared against the parsed result in evidence screenshots, and so a future re-parse is possible without re-calling the model. |
| `merchant` | `String?` | nullable | The merchant name extracted from the receipt. Nullable because the receipt may not show a merchant name, and the extraction prompt instructs the model to return null rather than guess. |
| `totalMinor` | `Int?` | nullable | The total in minor currency units (kobo, cents) as an integer. `Int` not `Float` because money is never stored as a decimal — floating-point arithmetic produces rounding errors on currency. Nullable because the total may not be legible. |
| `currency` | `String?` | nullable | ISO 4217 currency code (e.g. `NGN`, `USD`). Nullable because the currency may not be printed on the receipt. |
| `purchaseDate` | `DateTime?` | nullable | The date on the receipt. Nullable because it may not be legible. Stored as `DateTime` rather than `String` so it can be sorted and filtered if needed later. |
| `lineItems` | `Json` | not null | Array of line item objects (description, quantity, unitPriceMinor, amountMinor). Stored as JSON rather than a separate table because line items are always read and written as a complete set with their parent — never queried independently — and a join for every receipt view would add complexity without benefit. |

### `FollowupResult`

The text output from a follow-up action on an already-extracted receipt.

| Column | Type | Constraint | Decision |
|---|---|---|---|
| `receiptId` | `String` | FK → Receipt, `onDelete: Cascade` | Not unique (unlike ExtractionResult) — a user can run multiple follow-up actions on the same receipt. Indexed (`@@index([receiptId])`) because the status page fetches the latest followup for a receipt. |
| `jobId` | `String` | `@unique` | Ties this result back to exactly one Job row. Unique because one job produces exactly one followup result — a second result from the same job would be a bug. |
| `action` | `String` | not null | Which action was performed (`summarize`, `rephrase`, `expand`). Not nullable because every followup result was produced by a specific action — there is no case where a result exists without knowing which action created it. |
| `resultText` | `String` | not null | The model's plain-text response. Not nullable because a followup that produced no text is a failure, not a result — failures are recorded on the Job row, not here. |

## 5. The Concepts

### API Endpoints

**What it is.** An API endpoint is a specific URL that a client can send a request to, expecting the server to do something and send a response back. In this project, `/api/receipts/upload` is one — it's where the upload form sends the file.

**Why it is needed.** Without a defined endpoint, the browser has no agreed-upon address to send the upload to, and the server has no fixed place to listen for it. Every action the user takes (upload, check status, trigger a follow-up) needs its own endpoint because each does something different and needs different validation and logic.

**How I implemented it.** Each endpoint is a `route.ts` file under `app/api/`, using Next.js's App Router convention — the folder path becomes the URL path. `app/api/receipts/upload/route.ts` exports a `POST` function; Next.js wires that to `POST /api/receipts/upload` automatically.

**What I chose against, and why.** I could have put all the logic behind one endpoint with an `action` field in the body, dispatching internally. I didn't, because separate endpoints get separate, independent rate limits and validation — the brief specifically wants the upload endpoint and the follow-up endpoint rate-limited differently, which is much simpler with two real endpoints than one endpoint branching on a parameter.

### SDKs vs Raw HTTP

**What it is.** An SDK is a library the provider publishes that wraps their raw HTTP API in functions you call directly in your language, handling authentication headers, request formatting, and response parsing for you. Raw HTTP means constructing those requests yourself.

**Why it is needed.** Without the SDK, I'd have to hand-build the JSON request body for every Gemini call, manage the API key header myself, and parse the raw response — more code, more places to get the request shape wrong, and no help when Google changes something in their API surface.

**How I implemented it.** `@google/genai`, the official SDK, imported in `lib/ai/gemini.ts`. `ai.models.generateContent({...})` is the SDK call; I never touch a raw `fetch` to Google's endpoint.

**What I chose against, and why.** Raw HTTP calls via `fetch` directly to `generativelanguage.googleapis.com`. I chose the SDK because the brief requires official SDKs, and because the SDK gives typed request/response shapes — the `ThinkingLevel` enum type-checking error I hit while wiring config is a good example: the SDK caught a typo I would have shipped silently with raw JSON.

### System Prompts vs User Prompts

**What it is.** A system prompt sets the model's role and rules for the whole request — how it should behave. A user prompt is the actual input or question for this specific call.

**Why it is needed.** Without a system prompt, the model has no fixed instructions about output format, and I'd have to repeat the same rules (return JSON only, use minor units, never guess) inside every single request's user content — easy to get inconsistent across calls.

**How I implemented it.** `lib/ai/prompts/extraction.ts` and `lib/ai/prompts/followup.ts` each export a constant system prompt string, passed as `systemInstruction` in the `generateContent` config. The user content is just the receipt image (extraction) or the extracted JSON plus the requested action (followup).

**What I chose against, and why.** I could have folded the rules into the user prompt itself, prepended to every request. I didn't, because `systemInstruction` is a distinct field the SDK treats differently from user content, and keeping the rules separate from the per-request data makes it obvious in the code which part is fixed and which part changes per call.

### Model Parameters

**What it is.** Settings that control how the model generates its response — for example temperature (how much randomness to allow) and maxOutputTokens (the output length cap).

**Why it is needed.** Without setting these deliberately, the model uses its defaults, which are tuned for general conversation, not for a task like transcribing a receipt where I want the same input to produce the same output every time, and where I know roughly how much text the answer needs.

**How I implemented it.** Both roles' parameters live in `lib/ai/config.ts`: extraction runs at `temperature: 0` (deterministic — extraction is transcription, not authorship) with `thinkingLevel: LOW` and `maxOutputTokens: 2048`; followup runs at `temperature: 0.4` (slightly more natural phrasing, but the underlying facts are already fixed) with a smaller token cap.

**What I chose against, and why.** I originally left `maxOutputTokens` at 1024 with the default thinking level. That failed — Gemini 3 Flash Preview has thinking mode on by default, which consumes part of the output token budget on internal reasoning before it writes the actual answer, and the JSON came back truncated mid-object. I chose against the default thinking level specifically because extraction has nothing to reason through — it's reading, not solving — so paying for thinking tokens was pure waste that also broke the response.

### Structured Output and Schema Validation

**What it is.** Structured output means asking the model to return data in a fixed shape (JSON matching a schema) instead of free-form prose. Schema validation is checking that what came back actually matches that shape before trusting it.

**Why it is needed.** Without structured output, I'd get prose I'd have to parse with string matching, which breaks the moment the model phrases something slightly differently. Without validating what comes back, a model output that's almost-but-not-quite the right shape could crash later code or silently store wrong data — the JSON parse error I hit from the truncated response would have been a much worse bug if I hadn't been checking for it.

**How I implemented it.** I request Gemini's own schema enforcement (`responseSchema` in the config, pointing to `GEMINI_EXTRACTION_RESPONSE_SCHEMA` in `lib/ai/schemas/extraction.ts`), then separately validate the parsed JSON against a Zod schema (`extractionResultSchema`) in `lib/ai/gemini.ts` before I ever store it. If parsing or validation fails, it retries up to a configured limit, then the job is marked FAILED with the real error message.

**What I chose against, and why.** I chose against trusting the provider's schema enforcement alone. When the response actually came back truncated (thinking mode ate the token budget), Gemini had still "enforced" the schema request — it just couldn't finish. My own Zod validation is what caught that the JSON was malformed, and it's what makes the retry-then-fail path exist at all.

### Jobs and Workers

**What it is.** A job is a row in the database representing one unit of work to be done. A worker is a separate process that looks for jobs and does the actual work — in this case, calling Gemini.

**Why it is needed.** Without this split, the upload request itself would have to wait for Gemini to respond before it could reply to the browser — a slow, flaky external call sitting directly in the request path. If Gemini is slow or down, the whole upload endpoint hangs with it.

**How I implemented it.** The upload route creates a Job row with status PENDING and returns 202 Accepted immediately, without calling the model. `scripts/worker.ts` is a completely separate Node process, run with `npm run worker`, that polls the Job table on its own schedule and does the actual Gemini calls.

**What I chose against, and why.** I considered firing the extraction off in-process from the upload route without awaiting it (fire-and-forget). I chose the standalone worker instead because it survives the dev server restarting, and because it's what actually demonstrates "jobs and workers" as a real architectural pattern rather than a disguised synchronous call — which matters given this is literally one of the concepts I have to explain here.

### Queues, FIFO, and Why Concurrency Is Capped

**What it is.** A queue is an ordered line of pending work. FIFO ("first in, first out") means the oldest item in the queue gets handled first. Capping concurrency means limiting how many jobs the worker processes at the same time.

**Why it is needed.** Without ordering, jobs could be processed in any order, and a user who uploaded first could wait behind someone who uploaded later for no reason. Without a concurrency cap, uploading many files at once would fire that many simultaneous calls to Gemini — and my real account only allows 5 requests per minute on the extraction model, so an uncapped burst would just produce a wall of 429 errors instead of results.

**How I implemented it.** The worker's poll query is `WHERE status = PENDING ORDER BY createdAt ASC`, which is the FIFO ordering. It claims only `AI_CONFIG.queue.concurrency` jobs per poll (set to 3). I proved this holds by firing five uploads at once and watching the worker terminal process them in a batch of three, then pick up the remaining jobs on the next poll cycle, rather than all five hitting Gemini together.

**What I chose against, and why.** I could have let concurrency default to something higher, closer to my daily quota. I set it below my actual RPM limit specifically because a burst of retries under load could otherwise exceed even a concurrency-3 cap in a single minute — better to process a bit slower than to start failing calls I could have avoided.

### Rate Limiting as a Cost Control

**What it is.** Rate limiting restricts how many requests a given user or IP can make to an endpoint within a time window.

**Why it is needed.** Without it, a single user (accidentally or on purpose) could trigger unlimited Gemini calls, and each one costs money and counts against my daily quota — which, on the free tier, is a hard 20 requests a day on the extraction model. One careless retry loop could exhaust the entire day's budget in seconds.

**How I implemented it.** `lib/rate-limit.ts`, reused from Assessment 1's RateLimit table, keyed by IP and action name with a configurable window and limit. The upload endpoint and the follow-up endpoint have separate limits (`AI_CONFIG.rateLimits.processTrigger` and `.followupAction`), because they have different costs and different reasons someone might hit them repeatedly.

**What I chose against, and why.** I could have used a single shared rate limit across both endpoints. I kept them separate because the follow-up action is cheap and easy to click repeatedly by accident, while the upload endpoint is the more expensive one — a single shared limit would either be too loose on uploads or too strict on follow-ups.

### Why Files Live in Object Storage, Not the Database

**What it is.** Object storage (Cloudflare R2, in this case) is a service built specifically for storing files. Keeping files out of the database means the database only ever holds a reference (a "key") pointing at where the file actually lives.

**Why it is needed.** Storing file bytes directly in Postgres would bloat the database, slow down every query that touches that table, and make backups far larger than they need to be for no benefit — the database is good at structured rows, not binary blobs.

**How I implemented it.** `lib/storage/r2.ts` uploads the file to R2 and returns a key; only that key, plus metadata (filename, MIME type, size), is stored in the Receipt table. There is no column anywhere capable of holding the actual bytes.

**What I chose against, and why.** R2 has no official first-party SDK, so I used the official AWS S3 SDK pointed at R2's S3-compatible endpoint instead — the brief explicitly allows this ("where a provider has none for your platform, use a compatible official SDK"). I chose against storing files locally on disk because this needs to run the same way regardless of where it's deployed, and a local disk path wouldn't survive a deploy or a restart the way object storage does.

### Cost Model

**What it is.** An estimate of what running this feature actually costs, per use and in total, given real usage limits.

**Why it is needed.** Without knowing the cost per call, I could accidentally build something that's fine in testing but expensive or rate-limited into uselessness with real users — and on a free-tier account specifically, "cost" isn't just money, it's also the daily request quota running out.

**How I implemented it.** On the free tier, each full run (one extraction call plus one follow-up call) costs $0 in money but consumes 2 of my 20 daily extraction-model requests and 2 of 500 daily follow-up-model requests — so the extraction model's 20/day limit is the real daily ceiling, roughly 20 receipts a day on this account. On a paid tier, the same run would cost roughly [put your own rough number here once you check current Gemini 3 Flash pricing] per receipt.

**What I chose against, and why.** I chose against testing with unlimited runs, because I only had 20 extraction calls a day to work with — this is also why some of my testing had to be deliberate rather than run-it-until-it-works, and why I planned specific tests (one happy path, one deliberately broken) rather than looping freely.

## 6. What Went Wrong

### Problem 1: R2 uploads failing with AccessDenied

**The symptom.** The upload endpoint returned a 500 error. The server log showed `AccessDenied: Access Denied, HTTP 403`, thrown from `PutObjectCommand` in `lib/storage/r2.ts`.

**The investigation.** I checked whether the bucket name in `.env` matched the actual bucket in Cloudflare (it did). I checked whether the Account ID was correct (it was). I checked the R2 client's endpoint URL construction (correct).

**The cause.** The API token I'd created for R2 had Object Read only permissions, not Read & Write — I'd selected the wrong option when creating it.

**The fix.** Deleted the token, created a new one scoped to Object Read & Write on the specific bucket, updated the three `STORAGE_*` credentials in `.env`, restarted the dev server.

### Problem 2: The worker kept "succeeding" without ever calling Gemini

**The symptom.** After wiring in the real Gemini extraction call and having the agent overwrite `scripts/worker.ts`, jobs kept completing with `status: DONE` in about 3 seconds each — but the `ExtractionResult` table stayed completely empty no matter how many times I ran it.

**The investigation.** I checked the Job table directly via SQL — confirmed `type: EXTRACTION`, `status: DONE`, no errors. I checked whether the query was somehow pointed at the wrong database branch. I checked whether the `ExtractionResult` write itself had a bug in the upsert logic. All of that came back clean, which didn't make sense given the code should have written a row.

**The cause.** The agent had reported "I've completely overwritten scripts/worker.ts" but the file on disk still had the old stub code — the literal `setTimeout(resolve, 2000)` sleep-and-mark-done logic, never actually replaced. The running `npm run worker` process was executing that stale file the whole time, so "DONE" meant "slept for 2 seconds," not "called Gemini."

**The fix.** Opened the file directly myself and read its actual content rather than trusting the agent's report, confirmed it was stale, manually pasted in the correct code, and restarted the worker process (`tsx` doesn't hot-reload — a running process keeps whatever was loaded at startup, so even a correct file edit does nothing until the process is stopped and restarted).

### Problem 3: Gemini responses failing to parse as JSON

**The symptom.** The worker logged `SyntaxError: Expected ',' or '}' after property value in JSON at position 92`, on every one of three retry attempts, then marked the job `FAILED`.

**The investigation.** I first suspected the schema format passed to `responseSchema` was wrong — Gemini's schema format has historically required an uppercase `Type` enum in some SDKs rather than plain JSON-Schema-style lowercase strings. I checked the official `@google/genai` docs and confirmed lowercase `"type": "string"` etc. is actually correct for this SDK — that wasn't the bug.

**The cause.** Gemini 3 Flash Preview has "thinking" mode enabled by default, which spends part of the `maxOutputTokens` budget on internal reasoning before writing the actual answer. With `maxOutputTokens` set to 1024, thinking consumed most or all of that budget, and the JSON response was cut off mid-object — a syntax error early in the string is exactly what a severely truncated response looks like.

**The fix.** Set `thinkingLevel: ThinkingLevel.LOW` in the extraction role's config (extraction is transcription, not reasoning — there's nothing for the model to think through) and raised `maxOutputTokens` to 2048 as a safety margin.

### Problem 4: The follow-up summary spinner never resolved

**The symptom.** After clicking "Summarize," the page showed "Generating summary..." forever, even though the worker terminal confirmed the follow-up job had actually completed successfully within a few seconds.

**The investigation.** I checked the follow-up API route for bugs — none found, it correctly created the job and returned 202. I checked the worker logic for the `FOLLOWUP` branch — it correctly wrote a `FollowupResult` row. The backend was doing everything right; the problem had to be on the page itself.

**The cause.** The page's polling `useEffect` only ran its `poll()` loop while at least one of extraction or follow-up was "ongoing" (`PENDING`/`PROCESSING`). By the time the user clicked Summarize, extraction was already `DONE` and no follow-up existed yet, so the loop's exit condition had already been met and it had stopped scheduling itself. Clicking Summarize did one manual one-off status fetch, but nothing restarted the recursive polling — so even though the job finished moments later, nothing was left running to notice.

**The fix.** Added a `pollKey` state value that increments whenever a follow-up is triggered, and included it in the `useEffect`'s dependency array — bumping it forces a fresh polling chain to start, which then runs normally until the follow-up reaches `DONE` or `FAILED`.

## 7. What This Slice Does Not Handle

What breaks at scale. The worker assumes exactly one process running locally. Claiming a job is a read followed by a separate update, not one atomic operation — if two worker processes ran at once, both could claim the same PENDING job before either updates its status, and it would be processed twice. This is fine for a single local worker but would need a conditional update (claim only if still PENDING) or a real queue with row-level locking (e.g. Postgres SKIP LOCKED) before running more than one worker.

What would need adding before real users touched it. Free-tier Gemini usage means prompts and responses may be used to improve Google's products — receipts contain names, addresses, and partial card numbers, so a real deployment would need to move to a billed tier before handling anyone's actual financial data. The daily quota (20 extraction calls) is also far too low for real use; a production version needs a paid tier with proper rate-limit headroom. There's also no retry-on-restart for jobs that were PROCESSING when the worker crashed — they'd stay stuck in that state forever rather than being picked back up.

What was left out because it was outside the brief. No editing, sharing, exporting, or history view of past receipts — the brief explicitly asks for one flow, done properly, not a full receipts management app.

## 8. If I Built This Again

If I built this again, the biggest thing I'd change is writing the concurrency and retry logic against my actual Gemini quota from day one, rather than discovering the real 5-requests-per-minute, 20-requests-per-day limits partway through. I built the queue's concurrency cap and the extraction role's retry count against reasonable-sounding numbers before checking AI Studio's actual rate-limit page for this account — and the real numbers were far tighter than I assumed, which meant redoing config decisions that should have been correct the first time. Checking the real constraint before designing around an imagined one would have saved a redo and made every early test more meaningful, since I wouldn't have been unknowingly burning a scarce daily budget on numbers I'd have changed anyway.
